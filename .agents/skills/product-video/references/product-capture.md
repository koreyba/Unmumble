# Съёмка интерфейса продукта

Инструкция для этапа съёмки продуктового ролика. Читать, когда ролик требует демонстрации интерфейса. Продукт, устройство, URL, язык, сцены и папка результата задаются брифом; значения из предыдущей съёмки не являются обязательными настройками.

## Переносимый запуск из скилла

Основной путь для новой съёмки — самостоятельный Playwright из Node, без зависимости от Browser/Node REPL. Исполняемые помощники находятся **внутри скилла**: [capture-session.mjs](../scripts/capture-session.mjs) и [recorder.mjs](../scripts/recorder.mjs). Они не запускают приложение, не меняют его код и не устанавливают зависимости.

Скопируй [capture-config.json](../assets/capture-config.json) в папку нового ролика. Заполни `playwrightModule` путём к установленному `playwright/index.mjs`, `url` адресом реально запущенного приложения и `output` новой, ещё не существующей папкой сессии. В текущей установке кандидат модуля — `/Users/denys.koreiba/Documents/Unmumble.online/node_modules/playwright/index.mjs`; проверь существование перед запуском. Файловые пути разрешаются относительно JSON-конфига. Для mobile задай `device`, без отдельного `viewport`; для desktop убери device и задай viewport. Звук запрашивается только при `audio: true`.

```sh
node .agents/skills/product-video/scripts/capture-session.mjs /absolute/new-video/capture-config.json
```

Команда выше запускается из корня репозитория. Для глобальной установки используй фактический путь к `scripts/capture-session.mjs` внутри установленного скилла.

Без `scenario` выполняется короткая проба. Выход: `probe.png`, `session.json`, папка `probe/` с JPEG, `frames.txt`, `capture.json`, снимками меток и, если заказан звук, `tab-audio.webm`. Новая папка предотвращает перезапись принятой съёмки. Параметры устройства берутся один раз из полного профиля; helpers не открывают DevTools и не меняют viewport для размера финального видео.

Для полноценной съёмки сохрани отдельный доверенный локальный `.mjs` сценарий и укажи его в `scenario`. Он экспортирует `async run({page, context, startRecording, output})`. Сначала подготовь интерфейс и дождись фактической готовности, затем `const take = await startRecording('trainer', {readState})`; отмечай действия `await take.mark('before-back', selector)`, нажимай через Playwright, проверяй результат и вызывай `await take.stop()`. `readState(page)` необязателен, но полезен для продуктового состояния; специфичные селекторы остаются в сценарии. Помощник сам завершает незакрытую запись и закрывает браузер при завершении/ошибке. Не передавай длинные программы через TTY и не открывай помощник как сетевой eval-сервис.

В `capture.json` **все** `frames[].time`, `marks[].time`, `end` и `audioStart` отсчитываются в секундах от первого принятого кадра. Положительный audioStart означает, что звук начинается позже видео; отрицательный — раньше. Для новой записи вычисляй смещение заново. Архивный recorder имел иной формат времени кадров: не смешивай manifests разных версий.

Сначала проверь пробу через ffprobe и сохранённый кадр. Для простого исходника собирай `frames.txt` через FFmpeg concat с исходными временными интервалами, затем CFR 30 fps. Если выполняешь собственное пересэмплирование кадров, на каждом шаге выбирай последний кадр с временем не позже целевого, сохраняя общую длительность. Звук подгоняй по той же шкале времени, без изменения темпа носителя. Если нужна точная синхронизация длинной записи, проверь возможный дрейф отдельно.

При упаковке helpers проверены на отдельной тестовой странице: автоматический iPhone 13, реальный клик и изменение состояния, фильтрация размеров, единая шкала времени и сборка H.264/30 fps. Эта проверка выполнена без аудио; упаковка не заменяет новую пробу звука конкретной вкладки. Историческая успешная запись со звуком описана ниже.

При полном переходе на другую страницу recorder аудио в прежнем document теряется: заверши дубль до навигации и начни новый после неё. SPA-переход тоже проверь короткой пробой. При изменении импортированного recorder перезапускай Node-процесс: кеш модулей может оставить старый код.

## Подготовить продукт

1. Найти актуальную папку приложения, проверить ветку и commit, зависимости и команду локального запуска. Старый путь `ListenToLearn` в архивном `record.mjs` уже не существует; текущий репозиторий расположен в `Documents/Unmumble.online`. Перед новой съёмкой проверить пути заново.
2. По возможности использовать отдельную локальную копию с понятными демонстрационными данными. Проверить наличие каталога, нужной фразы и работоспособность проигрывателя.
3. Если локальная база показывает `no such table: catalog_phrase_analysis`, устранить проблему подготовки базы перед съёмкой. Миграции и dev-сервер должны использовать одну и ту же локальную базу, конфигурацию и каталог сохранения. Не считать пустой каталог успешной подготовкой и не применять миграции к production ради съёмки.
4. URL и порт брать из реально запущенного сервера. Порты 4173/4174 принадлежат прошлой записи.
5. Определить короткий перечень действий и наблюдаемый результат каждого. Для внешнего видеопровайдера заранее проверить воспроизведение нужного примера.

## Выбрать компоновку и звук

Размер записи интерфейса и формат финального ролика — разные настройки. Выбери `capture.layout` по задаче: `mobile` или `desktop`. Звук продукта нужен лишь при `capture.audio.enabled: true`; озвучка и музыка добавляются отдельно и не требуют захвата вкладки. При `false` пропусти запросы аудио, проверки аудиодорожки и синхронизацию с ней. При переиспользовании записи исключи её звук из монтажа, если он отключён в брифе.

### Desktop

Для новой сессии используй обычный desktop-контекст без мобильного профиля, мобильного UA и touch-эмуляции. Задай CSS viewport под естественную компоновку продукта, например 1440×900, и проверь его на снимке. Это пример, а не обязательный размер:

```js
const browser = await chromium.launch({headless: false});
const context = await browser.newContext({viewport: {width: 1440, height: 900}});
const page = await context.newPage();
```

Для существующей вкладки убедись, что мобильная эмуляция выключена; сохраняй подходящий размер, если пользователь уже настроил его. Вертикальный экспорт desktop-интерфейса делай через кадрирование/композицию в монтаже, не превращая его шириной viewport в мобильную версию. Если целевая кнопка или результат не помещаются, пересмотри кадрирование. Новый desktop-маршрут требует пробы; историческая iPhone-запись не является его проверкой.

### Mobile: настроить один раз

Для новой съёмки предпочитай проверенный автоматический запуск; существующую вкладку переиспользуй, если она уже корректно настроена. Выбрать один способ настройки для конкретной съёмки:

- **Новая автоматическая сессия:** создать контекст с полным профилем `devices[deviceName]` или использовать помощник скилла. Новый запуск должен пройти короткую проверку картинки и, если нужен, звука.
- **Уже настроенная вкладка:** сохранить выбранный iPhone в DevTools без `setViewportSize` и без второй эмуляции через CDP.

Пример создания нового контекста:

```js
const browser = await chromium.launch({headless: false});
const context = await browser.newContext({...devices[deviceName]});
const page = await context.newPage();
```

Не добавлять второй независимый размер viewport к выбранному мобильному профилю без конкретной причины. Финальные 1080×1920 — размер монтажной композиции, а не ширина страницы продукта. Увеличение мобильного viewport до 1080 CSS-пикселей меняет адаптивную компоновку.

До записи сохранить один скриншот и фактические `innerWidth`, `innerHeight`, `devicePixelRatio`, user agent. Проверить читаемость кнопок, отсутствие горизонтального переполнения и видимость целевого действия. Масштаб DevTools «Fit to window» не заменяет проверку этих параметров.

## Сначала короткая проба

Снять 3–5 секунд с одним действием. Проверить сохранённые файлы: картинка соответствует выбранной desktop/mobile компоновке, реакция видна. Если звук продукта включён, воспроизвести его и проверить наличие, слышимость и синхронизацию. При неудаче выяснить причину до полной съёмки. Не запускать несколько браузеров с разными настройками без нового диагностического вывода.

## Записать изображение и звук

**Проверенное изображение:** `context.newCDPSession(page)` → `Page.startScreencast`; сохранять кадры, подтверждать `Page.screencastFrameAck`, сохранять время каждого кадра. В прошлой записи использовались JPEG, quality 95 и ограничения maxWidth 1080/maxHeight 1920. Эти ограничения не гарантируют такое разрешение исходного кадра: проверить реальные размеры файлов.

Из кадров собрать видео с сохранением их временных интервалов через FFmpeg concat. При обычном `recordVideo` Playwright сохранять видео после закрытия контекста; отдельно проверить размер, поскольку настройка записи может масштабировать картинку.

**Звук, только если включён:** проверенный в прежней записи способ — захват вкладки через `getDisplayMedia` с аудио, затем `MediaRecorder` для её аудиодорожек. Использовались `preferCurrentTab: true`, `selfBrowserSurface: 'include'` и `suppressLocalAudioPlayback: false`. Выбор источника зависит от браузера и разрешений; убедиться, что выбрана нужная вкладка и есть аудиодорожка. Следующие два абзаца относятся только к записи со звуком.

Звук сохранять отдельно в `tab-audio.webm`. Его наличие не доказывается одним запросом разрешения: проверить дорожку и прослушать пробу. Варианты с автоматическим выбором вкладки по заголовку сначала проверять в текущем браузере; не считать старые launch-флаги гарантией захвата.

Зафиксировать единую временную шкалу кадров, сцен и начала аудиозаписи. В успешной записи `audioStart` равен 5.492 секунды после первого кадра. Для новой записи вычислять это значение заново; не копировать его. Видеофрагмент и его звук вырезать по согласованным исходным меткам.

## Действия и подтверждения

- Находить элементы по актуальной странице: роль, название, placeholder или устойчивый идентификатор. Архивные селекторы относятся к прежней версии продукта.
- Ожидать готовность данных и активную кнопку, для сцен с проигрывателем — фактическое воспроизведение, затем выполнять действие. Паузы оставлять для просмотра результата; не заменять ими проверку готовности.
- Сохранять видимый результат и, где доступно, состояние до/после действия. В `capture.json` прошлой записи подтверждены возврат к предыдущему субтитру, включение Repeat, скорость 1 → 0.75 и смена видео.
- Для текущего Unmumble фильтр Real phrases имеет role `radio`, не `button`; после выбора проверить обновлённый каталог. Плеер прокручивать через `.caption-box.scrollIntoView({block: "start"})`: прокрутка может принадлежать внутреннему контейнеру, а не window. Проверять селекторы в новой версии.
- После Replay состояние 3 означает buffering. Не переключать Play/Pause только потому, что состояние ещё не 1: нажимать лишь при актуальном aria-label `Play playback`, затем дождаться фактического воспроизведения.
- Для Unmumble: возврат возможен к уже загруженной фразе; заранее дождаться истории субтитров. Переход вперёд по незагруженным субтитрам не демонстрировать как доступную функцию.
- Чтобы показать повторение фразы, снять два полных цикла. В старой записи подтверждено включение Repeat, но два полных цикла не зафиксированы. Не подменять демонстрацию работающего цикла дублированием фрагмента на монтаже.

## Съёмка для последующего монтажа

Для каждого действия записать чистый кадр до нажатия, реальную реакцию и время после неё. Оставить запас по краям для склеек и достаточное разрешение для приближения. В сценах со звуком записать хорошо слышимые примеры.

В финальном ролике курсор, стоп-кадры и zoom-in/zoom-out добавлялись в Remotion; реакции продукта и речь взяты из реальной записи. Не делать декоративные зумы изменением viewport во время съёмки. Маркер клика можно добавлять при записи или монтаже — выбрать один способ, чтобы не получить два маркера.

Ожидания загрузки сокращать согласованными склейками картинки и имеющегося звука. Убирать подсказки и элементы управления видеоплеера штатным исчезновением перед чистым фрагментом, если это возможно. Не менять функциональность продукта ради демонстрации.

## Передать в монтаж

Передать исходную запись, сценовые снимки и manifest: URL, текущую ветку/commit и dirty-состояние репозитория, выбранную компоновку/устройство, размеры страницы и кадров, времена действий, подтверждённые результаты и ограничения. Не подставляй старый sourceCommit: сохранённая метка приложения при hot reload может не описывать реально снятый код. При наличии звука передать отдельную дорожку и её смещение; при отсутствии отметить `audio.enabled: false`, а не ошибку записи. Сохранять исходники отдельно от монтажных версий.

Перед использованием архивного `record-existing.mjs` адаптировать жёстко заданные папку результата, commit, фразу и селекторы под текущую задачу. Сам по себе этот файл не является универсальной командой запуска.

Официальные справки для новой реализации: [эмуляция устройства](https://playwright.dev/docs/emulation), [запись видео](https://playwright.dev/docs/videos). Доступность встроенного Browser/Node REPL проверять отдельно: эта инструкция не исправляет подключение инструментов. Для съёмки можно использовать самостоятельный Playwright CLI, если он доступен.
